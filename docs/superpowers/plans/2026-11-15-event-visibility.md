# Free events (Save-only) and Public/Private events Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A free event is a Save-only listing with a saves count for its host; a host can mark any event Private, which hides it from every list but keeps it open to anyone with its share link.

**Architecture:** Database first (four migrations, pgTAP before each), then the Flutter app (models, repositories, screens), then the two journeys. One filter in `events.tab_rows` hides private events from Home, View all and the map; the open RLS policy and the host-page lists get the same filter; reads by someone who already has the event (tickets, saved, chat, reviews) stay on `security definer` functions and are pinned by tests with a private event.

**Tech Stack:** Supabase Postgres (pgTAP, `supabase test db`), Flutter 3.47.9 with Riverpod and go_router, `flutter drive` journeys through `tools/e2e.sh`.

**Spec:** `docs/superpowers/specs/2026-11-14-event-visibility-design.md` (owner decisions in `docs/decisions/2026-11-10-fiuu-and-pending.md`).

## Global Constraints

- Branch `feat/event-visibility`, cut from `claude/admiring-volta-g8kv4w`. No PR, no push to `claude/admiring-volta-g8kv4w`, no change under `.github/workflows` (CI is pinned to Flutter 3.47.9).
- New migrations are numbered after the latest in `supabase/migrations` (0111 on this base): `0112` to `0115`. The manual-payment work (`docs/superpowers/specs/2026-11-14-manual-payment-design.md`) also changes `bookings.create_booking`; here only the free refusal (`free_event_no_booking`) and the visibility changes are added, never the hold or cooldown.
- "Free" in the app means `price_sen = 0` or `accept_bookings = false` (`EventDetail.isBookable == false`, `events.is_bookable`).
- `share_code`: 10 characters, letters and digits, unique, unguessable, generated by a column default and backfilled.
- Visibility can change at any time, also after guests booked; it is not a locked field. Guests who booked keep their tickets.
- Private events never appear in Explore, View all, search, the map or the host's public page. A private event is readable by id through definer functions only (`event_detail`, `cards`, `event_brief`, `toggle_save`, `create_booking`); the code is the only way to learn the id.
- Every test is written first and watched failing. Database: `supabase test db <file>`; whole suite `tools/test_db.sh`. Flutter: `cd app && flutter test <file>`, whole suite `flutter test`; format and `flutter analyze` must stay clean.

## Review Focus

- A private event must still show in `my_bookings`, `booking_brief`, `chat.my_threads`, Saved, `reviews` and notifications for the people who have it (tests in Task 4).
- `identity.saved` in the app reads `events.events` through RLS; a private saved event would vanish. It moves to `events.cards` (Task 8).
- Turning an event Private after guests booked must not break their tickets or the host's guest list (Task 4 test).
- `saves_count` must not leak to guests or anon (Task 1).
- Existing tests that book a free event break on the refusal; each is moved to a paid event, not weakened (Task 1).
- `events.host_page` must not list a private event even for its own host's public page (Task 3).
